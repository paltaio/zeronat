Overview

zeronat exposes ports on a machine behind CG-NAT through a Linux host with a public IP. It needs no account or hosted control plane.

The server runs on the public host. The client runs behind NAT, dials out, and holds one control connection. Traffic hitting a public port on the server is forwarded to the matching local service on the client. Noise authenticates and encrypts each connection. The server keeps its private identity secret, each authorized client has its own credential, and remote administration uses an independent secret. Forwarding is terminate-and-forward at L4.

Install

curl -fsSL https://paltaio.github.io/zeronat/get.sh | sh

The installer configures Docker, systemd, OpenRC, or procd, generates the 32-byte server identity, client credential, and admin secret from the operating system random source, then prints a client enrollment command. The launcher resolves an exact release, verifies its Minisign manifest, and checks the platform package length and SHA-256 digest before running the bundled installer.

IMAGE="ghcr.io/paltaio/zeronat@sha256:<64-hex-image-digest>"
docker pull "$IMAGE"

Use the image digest published with the release. Compose requires ZERONAT_IMAGE to contain the digest reference.

Quick start

Install the server first. It stores the server identity, one client credential, and the admin secret in /etc/zeronat/.env. It prints an enrollment command containing the server public identity but no reusable credential.

# On the public host:
curl -fsSL https://paltaio.github.io/zeronat/get.sh | \
  sh -s -- --server --method systemd --ports "443/tcp 80/tcp 51820/udp" -y
# On the public host:
curl -fsSL https://paltaio.github.io/zeronat/get.sh | \
  sh -s -- --server --method docker --ports "443/tcp 80/tcp 51820/udp" -y

On the host behind CG-NAT, run the enrollment command printed by the server installer. Enter ZERONAT_CLIENT_SECRET from the server's protected /etc/zeronat/.env at the hidden prompt. Every identity and credential is 64 hexadecimal characters encoding 32 bytes.

The manual examples below use these shell variables. Replace each placeholder with the matching value from the protected installer state or enrollment output.

SERVER_SECRET="<64-hex-server-private-identity>"
SERVER_PUBLIC="<64-hex-server-public-identity>"
CLIENT_CREDENTIAL="<64-hex-client-credential>"
ADMIN_SECRET="<64-hex-admin-secret>"
IMAGE="ghcr.io/paltaio/zeronat@sha256:<64-hex-image-digest>"
IMAGE_SHA="<published-commit-sha>"

Open the control port (2222, UDP and TCP) on the server firewall. UDP carries the preferred KCP transport and stateless datagrams; TCP is the fallback. Both listeners apply bounded admission before allocating authenticated session state.

Upgrade and credential migration

Protocol 6 rejects older handshakes. A mixed-version server and client do not connect, and there is no legacy credential fallback.

For an installation that used one shared secret, open the fresh-install wizard on the public server:

curl -fsSL https://paltaio.github.io/zeronat/get.sh | sh -s -- --reinstall

Configure the server again and choose Generate new for its identity. Save the client enrollment command it prints. That command enrolls one client when supplied the generated ZERONAT_CLIENT_SECRET. To authorize multiple clients, configure a separate [[clients]] entry with a unique id and credential for every client, including that first generated credential, as described under Multi-client routing. A nonempty [[clients]] list replaces the single authorization from the installer environment. Run the enrollment command on each client and enter its own credential at the hidden prompt. Forwarding is interrupted after the server changes protocol until every client is enrolled.

After migration, zeronat upgrade --check reports whether a newer signed release is available and zeronat upgrade applies it. The upgrader rejects legacy shared credentials, unknown installed versions, unsigned metadata, wrong-version assets, and digest mismatches.

Forwarding

On the server, --tcp PORT and --udp PORT name the public ports to expose. On the client, the same flags take a forward spec mapping that public port to a local target:

Client specForwards to
--tcp 443127.0.0.1:443
--tcp 443:8443127.0.0.1:8443
--tcp 443:10.0.0.5:44310.0.0.5:443

--udp works the same way. Both flags are repeatable.

Proxy protocol

Any client forward spec takes appended modifiers: SPEC[+proxy][+idle=SECS]. +proxy applies to TCP forwards only and is rejected on --udp; the client flag --proxy enables it on every --tcp forward at once. For each public connection, the client writes a PROXY protocol v2 header as the first bytes to the local target, carrying the real public peer address and the public listener address the connection arrived on. The target must be configured to expect the header; one that is not reads it as garbage at the start of every connection.

ZERONAT_SECRET="$SERVER_PUBLIC" ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
zeronat client --server <public-ip>:2222 --tcp 443:10.0.0.5:443+proxy+idle=600

Both ends must run a release that supports +proxy. After connecting, the client announces its per-forward options and waits for the server's acknowledgment; against a server that never acknowledges, the client logs an error naming the affected forwards and those forwards refuse every connection rather than relay without the header. Removing +proxy and restarting the client restores plain relaying against any server.

Traefik cutover

For a deployment where the forward's target is Traefik: configure Traefik to trust PROXY headers from the address the zeronat client dials from (on a Docker network typically the bridge gateway, e.g. 172.18.0.1) and restart it, then add +proxy to the client's forward specs and restart the client. Rollback is removing +proxy again; no Traefik change is needed.

# traefik static configuration
entryPoints:
  websecure:
    address: ":443"
    proxyProtocol:
      trustedIPs:
        - "172.18.0.1/32"

Traefik serves connections without a header even when trustedIPs is set, so the two restarts can happen in either order. Any host matching trustedIPs can forge client addresses; keep it a /32.

Once headers flow, IP-keyed middleware (geoip, allow and deny lists, rate limits) sees real public addresses; rules that matched the internal dial source stop matching.

Transparency

Per-port forwarding relays payload bytes untouched, but a service behind zeronat observes its network environment differently than the same service on a public IP:

BehaviorOn a public IPBehind zeronat
TCP client addressReal peer addressThe client's dial source; real address via +proxy
UDP peer addressReal peer address per datagramThe client's local socket, one per public source
Destination addressThe public IP and portThe forward's target address
TLSTerminated by the serviceSame: passthrough, never terminated or inspected
TCP half-closeOne direction keeps flowingNot propagated: a FIN closes both directions
Reset vs orderly closeRST visible as a resetA reset surfaces as an orderly close
Idle TCP lifetimeUnlimitedUnlimited while the tunnel is healthy
Idle UDP flow lifetimeNo flow state keptSource forgotten after max(180s, idle+60s)
IPv6As deployedPublic listeners are IPv4-only
UDP datagram sizePath MTU1442 bytes on a 1500 path over the UDP transport
Client disconnectedConnection refusedTCP: accepted then closed; UDP: silently dropped

With +proxy, the PROXY v2 header carries the real peer and the public listener address, so a parsing target recovers both. There is no PROXY protocol for UDP; when a UDP service needs real peer addresses, use --tun.

Both relay ends probe every half idle window, so a healthy idle stream lives until its path goes fully silent, probes included, for a whole window (default 120s, +idle=SECS per forward). +idle also extends the UDP source lifetime; a forgotten source returns through a fresh client socket, so the target sees a new source port.

The 1442-byte UDP limit is a 1500-byte path minus IPv4/UDP headers and tunnel framing. A WireGuard peer behind a forwarded port adds 32 more bytes: keep its MTU at 1410 or lower. The TCP transport has no per-datagram limit below 64 KB; loss becomes retransmission delay instead of drops.

Health checks: with no client connected, a TCP listener accepts and immediately closes, while a down service refuses.

Transport

The tunnel runs over UDP/KCP by default and falls back to TCP when the UDP handshake gets no reply. Both share the control port (2222). The client picks the transport with --transport auto|udp|tcp (default auto).

  • UDP (KCP): reliable ARQ over UDP carries the control channel and TCP-forward data; loss-tolerant UDP forwards ride as raw datagrams.
  • TCP: fallback for networks that block or break UDP.

Multi-client routing

Multiple clients can connect to one server. A route maps a listener (bind_ip, proto, port) to a client id. New connections go to the routed client; connections already open on the previous client drain until they close. There is no round-robin, health checking, or failover.

The server assigns a client id from the [[clients]].id or --client entry associated with the authenticated credential. Routes use that server-assigned id. The client's --id option changes only its locally derived label.

Load listeners, routes, and identity from a file with --config:

ZERONAT_SECRET="$SERVER_SECRET" zeronat server --config /etc/zeronat/server.toml
docker run -d --name zeronat --restart unless-stopped --network host \
  --user 65532:65532 --cap-drop ALL --security-opt no-new-privileges \
  -v /etc/zeronat/data:/etc/zeronat/data --env-file /etc/zeronat/.env \
  "$IMAGE" server --config /etc/zeronat/data/server.toml
# server.toml
[server]
id = "zn01"
control = "0.0.0.0:2222"
admin_secret = "<64-hex-admin-secret>"

[[clients]]
id = "rpi-2-ab12"
secret = "<64-hex-client-credential>"

[[listeners]]
bind_ip = "0.0.0.0"
proto = "tcp"
port = 8080

[[routes]]
bind_ip = "0.0.0.0"
proto = "tcp"
port = 8080
client = "rpi-2-ab12"

The server identity secret remains in ZERONAT_SECRET. Each [[clients]] entry authorizes one id and credential. [server].admin_secret authorizes remote admin and is optional; remote admin is disabled when it is absent.

CLI --tcp/--udp forwards merge with the file's listeners. To change the topology, edit the file and restart the server. A malformed config aborts startup.

Client config

Load servers, forwards, and identity from a file with --config:

zeronat client --config /etc/zeronat/client.toml
# client.toml
[client]
id = "rpi-2"
active = "home"

[[servers]]
name = "home"
addr = "203.0.113.7:2222"
secret = "<64-hex-server-public-identity>"
credential = "<64-hex-client-credential>"
transport = "auto"

[[servers]]
name = "backup"
addr = "dht"
secret = "<different-64-hex-server-public-identity>"
credential = "<different-64-hex-client-credential>"

[[forwards]]
proto = "tcp"
port = 443
target = "127.0.0.1:8443"
proxy = true
idle = 600

[[pppoe]]
name = "wan"
username = "user@isp"
password_file = "/etc/zeronat/wan.pass"

Replace each identity and credential placeholder with 64 hexadecimal characters encoding 32 bytes. The server identity and client credential in one profile must differ.

Each [[servers]] entry is a named profile with its own address, server public identity, client credential, and transport; [client].active picks the one to dial (default: the first). [[forwards]] entries take the same options as the CLI specs: proxy is TCP-only, idle is whole seconds. enabled = false keeps a forward in the config but stops serving it (default true). A [[pppoe]] entry names a session that can be spawned at runtime; one may set autostart = true to dial at boot when no forwards are declared. [tap] or [tun] declares a device mode instead, exclusive with forwards and PPPoE. A [tun] carrying exit_via and a [peer] table declare peer sessions, which run alongside the forwards and PPPoE sessions.

A file that declares any servers, forwards, PPPoE sessions, or a device is authoritative for the whole client shape: the matching CLI flags are ignored, each with a log line. A file that declares none leaves the CLI flags in charge. Scalars apply either way; the file's id overrides --id.

A missing file is a normal first boot. A file that fails to parse is moved aside to <name>.corrupt-<timestamp> and the client starts from the command line. A file that parses but contradicts itself (an active naming no server, duplicate server names, duplicate proto/port forwards, two autostart entries) aborts startup, as does an unreadable file.

The file carries client credentials; keep it mode 600. password_file keeps the PPPoE password out of the config.

Admin

Inspect a running server's topology over the control port (read-only):

ZERONAT_ADMIN_SECRET="$ADMIN_SECRET" zeronat admin --server <public-ip>:2222 show
# The admin secret comes from the container's protected env file:
docker exec -it zeronat /zeronat admin --server <public-ip>:2222 show

The client credential cannot open remote admin, and the admin secret cannot register a client or open a data path. Without an admin secret, the server continues forwarding but refuses remote admin.

It prints the server, its routes, connected clients, and active listeners. Each client lists the forwards it announced with non-default options (tcp:443 +proxy+idle=600), and a route shows its forward's options in the OPTIONS column.

On a terminal the same command opens an interactive console. Its PAIRS panel lists the peer pairs the server formed: the consumer, the provider, the capability, and whether the pair settled direct or relayed.

Client admin

Drive a running client over its local admin socket:

zeronat client admin                       # interactive console on a terminal
zeronat client admin show                  # print status and exit
zeronat client admin select-server backup
zeronat client admin disable-forward tcp:443
zeronat client admin add-server backup2 203.0.113.9:2222   # identity and credential from stdin
zeronat client admin spawn-pppoe wan
docker exec -it zeronat /zeronat client admin           # interactive console
docker exec -it zeronat /zeronat client admin show      # print status and exit
docker exec -it zeronat /zeronat client admin select-server backup
docker exec -it zeronat /zeronat client admin disable-forward tcp:443
docker exec -it zeronat /zeronat client admin add-server backup2 203.0.113.9:2222
docker exec -it zeronat /zeronat client admin spawn-pppoe wan

The socket is /run/zeronat/client.sock, or $XDG_RUNTIME_DIR/zeronat/client.sock when the client cannot create /run/zeronat; --socket overrides it and [client].control pins it. Access control is the filesystem: the socket is mode 600 in a 700 directory, so whoever can open it drives the client; no secret is needed.

The console lists the configured server profiles with the link state on the active one, the active session (mode and, for PPPoE, the link phase), and the forwards with their options. Its PEERS panel, printed as Peer slots by show, lists each peer slot: the capability, the peer on a consumer slot or provider on a providing one, the interface, the link state, and the path once the pair settles. Selecting a server tears the current session down and redials it against the new one, with a brief link drop. select-server, server-list edits, and forward edits persist to the config file when the client booted from one; spawn-pppoe/stop-pppoe are runtime-only and do not survive a restart.

add-server and remove-server edit the server list on a running client. add-server reads the server public identity on the first stdin line and the client credential on the second. A terminal prompts without echo. Neither value is taken on the command line. Removing the active profile is refused; select another first. enable-forward and disable-forward flip one forward without removing it: a disabled forward stays in the config and the status listing but refuses connections until re-enabled.

add-forward and remove-forward edit the forward list itself. add-forward tcp:8443:10.0.0.5:8443+proxy takes the same spec as --tcp/--udp and starts serving at once, even on a client that booted with no forwards. A running PPPoE session is left alone; the forward starts serving once that session stops. remove-forward tcp:8443 drops the port; connections open on it are cut. Changing a target is remove then add.

disconnect parks the client offline: the session tears down, nothing is dialed, and only the admin socket stays up. connect brings the boot-declared session back, optionally naming another server, and reports the resulting mode. Offline is never persisted; a restarted client serves what the file declares.

All ports

--tun forwards every port plus ICMP to one client over an L3 tunnel, instead of naming ports. The server sends all inbound traffic except the control port (and any --except ports) to the client and source-NATs the replies; the tunnel subnet is derived from the server public identity. Both ends need --tun; it cannot be combined with --tcp/--udp or --tap.

# Server: forward every port to the client, keep SSH on 22:
ZERONAT_SECRET="$SERVER_SECRET" ZERONAT_CLIENT_ID=client \
ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
zeronat server --control 2222 --tun --except 22

# Client (behind CG-NAT): local services receive on the same port:
ZERONAT_SECRET="$SERVER_PUBLIC" ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
zeronat client --server <public-ip>:2222 --tun
# Server: forward every port to the client, keep SSH on 22:
docker run -d --name zeronat --restart unless-stopped --network host \
  --user 0:0 --cap-drop ALL --cap-add NET_ADMIN --security-opt no-new-privileges \
  --device /dev/net/tun -e ZERONAT_SECRET="$SERVER_SECRET" -e ZERONAT_CLIENT_ID=client \
  -e ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" "$IMAGE" \
  server --control 2222 --tun --except 22

# Client (behind CG-NAT): local services receive on the same port:
docker run -d --name zeronat --restart unless-stopped --network host \
  --user 0:0 --cap-drop ALL --cap-add NET_ADMIN --security-opt no-new-privileges \
  --device /dev/net/tun -e ZERONAT_SECRET="$SERVER_PUBLIC" \
  -e ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" "$IMAGE" \
  client --server <public-ip>:2222 --tun

Forwarded traffic includes the server's own SSH; keep it reachable with --except <ssh-port> (repeatable). The client needs no NAT: local services receive the traffic on the same port and must listen on 0.0.0.0 or the tunnel address.

Linux only. The server needs root or CAP_NET_ADMIN, /dev/net/tun, and nft or iptables to program the NAT.

Exit mode

On top of --tun, the server's --exit makes it a default-route exit: it masquerades the client's outbound traffic onto its own uplink. --exit-iface <IF> names the interface to masquerade out of; without it the server takes the interface its default route uses. [server] exit and exit_iface set both from the config file.

On the client, --exit routes this host's IPv4 traffic through the tunnel. The server's address is pinned to the current default route as a /32, and 0.0.0.0/1 plus 128.0.0.0/1 point at the tun device, so they beat the host's own default route on prefix length while leaving it in place. --exit-strict goes further: it deletes the original default routes and puts ::/1 and 8000::/1 on loopback for as long as the tunnel routes are up, so traffic stops rather than leaking out the uplink if the tunnel drops. IPv6 sends fail on the host with ENETUNREACH, and the two routes read as ordinary dev lo entries in ip -6 route. Teardown restores the defaults and removes both; a crash skips it and leaves the host without a default route.

# Server: masquerade the client's traffic out eth0:
ZERONAT_SECRET="$SERVER_SECRET" ZERONAT_CLIENT_ID=client \
ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
zeronat server --control 2222 --tun --except 22 --exit --exit-iface eth0

# Client: send this host's IPv4 traffic through the server:
ZERONAT_SECRET="$SERVER_PUBLIC" ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
zeronat client --server <public-ip>:2222 --tun --exit --exit-strict
# Server: masquerade the client's traffic out eth0:
docker run -d --name zeronat --restart unless-stopped --network host \
  --user 0:0 --cap-drop ALL --cap-add NET_ADMIN --security-opt no-new-privileges \
  --device /dev/net/tun -e ZERONAT_SECRET="$SERVER_SECRET" -e ZERONAT_CLIENT_ID=client \
  -e ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" "$IMAGE" \
  server --control 2222 --tun --except 22 --exit --exit-iface eth0

# Client: send this host's IPv4 traffic through the server:
docker run -d --name zeronat --restart unless-stopped --network host \
  --user 0:0 --cap-drop ALL --cap-add NET_ADMIN --security-opt no-new-privileges \
  --device /dev/net/tun -e ZERONAT_SECRET="$SERVER_PUBLIC" \
  -e ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" "$IMAGE" \
  client --server <public-ip>:2222 --tun --exit --exit-strict

--exit requires --tun on both ends; --exit-iface and --exit-strict require --exit. In the config file, [server] exit_iface and [tun] exit_strict carry the same requirement.

L2 bridge (TAP)

--tap relays raw Ethernet frames over the tunnel, joining a TAP on each end into one L2 segment. It carries anything Ethernet, including PPPoE. Both ends need --tap; it cannot be combined with --tcp/--udp.

# Near the target segment (e.g. the PPPoE concentrator):
ZERONAT_SECRET="$SERVER_SECRET" ZERONAT_CLIENT_ID=client \
ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
zeronat server --control 2222 --tap zn0 --bridge br0

# Behind CG-NAT, then run e.g. pppd on zn0:
ZERONAT_SECRET="$SERVER_PUBLIC" ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
zeronat client --server <public-ip>:2222 --tap zn0
pppd plugin rp-pppoe.so zn0 user <user>
# Near the target segment (e.g. the PPPoE concentrator):
docker run -d --name zeronat --restart unless-stopped --network host \
  --user 0:0 --cap-drop ALL --cap-add NET_ADMIN --security-opt no-new-privileges \
  --device /dev/net/tun -e ZERONAT_SECRET="$SERVER_SECRET" -e ZERONAT_CLIENT_ID=client \
  -e ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" "$IMAGE" \
  server --control 2222 --tap zn0 --bridge br0

# Behind CG-NAT; zn0 lands in the host netns, run pppd on the host:
docker run -d --name zeronat --restart unless-stopped --network host \
  --user 0:0 --cap-drop ALL --cap-add NET_ADMIN --security-opt no-new-privileges \
  --device /dev/net/tun -e ZERONAT_SECRET="$SERVER_PUBLIC" \
  -e ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" "$IMAGE" \
  client --server <public-ip>:2222 --tap zn0
pppd plugin rp-pppoe.so zn0 user <user>

--bridge <name> enslaves the TAP to an existing bridge; --tap-mtu <n> sets the MTU (default 1400). Linux only. Needs CAP_NET_ADMIN: root, setcap cap_net_admin+ep zeronat, or Docker --cap-add NET_ADMIN --device /dev/net/tun (plus --device /dev/ppp for pppd).

The installer can build that bridge on netplan or systemd-networkd hosts: pass --bridge-nic <iface> (or pick the interface in the wizard) and it creates the bridge, enslaves the NIC, and persists the change. On a single-NIC server, where the uplink itself must join the bridge, it moves that interface's address onto the bridge and waits for you to confirm you still have access, reverting within ~30s if you do not.

Peer sessions

Two clients of one server can run a session with each other. One side provides a capability, the other names that side by client id; the server pairs them and both ends try a UDP punch. A pair that punches through runs directly between the two hosts, and one that does not runs over the server. A client on the TCP transport never punches, so its pairs are always relayed.

The clients authenticate the peer identities assigned to their credentials and derive fresh traffic keys for each pair. A relayed pair moves ciphertext the server passes without opening it. A direct pair and a relayed pair have the same payload protection.

Peer slots run beside the client's own session with the server and pair while that client serves forwards or sits idle. Under a --tun, --tap, or PPPoE session the slot is recorded and pairs when the client returns to either.

A server started with only --control registers clients and pairs them. It carries no forwards, TAP or tun of its own, so the control port is the only one to open. The server config must authorize each peer under a different [[clients]] id and credential.

Peer exit

The provider sets exit = true under [peer], with an optional exit_iface naming the interface to masquerade out of (default: the default-route one). It opens a tun (znx0) on the pair's subnet and masquerades the consumer's traffic onto its uplink. The consumer names the provider with exit_via under [tun]; exit and exit_strict route this host's traffic through the pair the same way they route it through a server. One exit provider serves one consumer at a time; a second is refused while that pair is up.

# provider client.toml: serve one peer an exit
[peer]
exit = true
exit_iface = "eth0"

# consumer client.toml: route through that peer
[tun]
exit = true
exit_strict = true
exit_via = "office-b1c2"

A [tun] that names exit_via describes the peer session, so the same client cannot also run a server tunnel from it, and the table takes no address. dev names the consumer's device (default zn0). The forwards and PPPoE sessions in the same file keep running against the server.

L2 segment

A segment provider sets segment under [peer] to the bridge carrying the segment it shares. It opens a TAP (zns0), enslaves it to that bridge, and switches Ethernet frames between the bridge and every consumer attached to it. Several consumers can share one segment provider.

# provider client.toml
[peer]
segment = "br0"

znpppoe --peer <client-id> is the consumer for a segment: it opens its PPPoE sessions over that peer's segment instead of a bridge port on the server. See PPPoE proxy.

Attaching at runtime

The client admin attaches and detaches peer slots on a running client:

zeronat client admin attach-provider exit eth0     # serve peers an exit
zeronat client admin attach-provider segment br0   # serve peers an L2 segment
zeronat client admin attach-peer office-b1c2 --dev zn0 --exit --exit-strict
zeronat client admin detach-peer office-b1c2
zeronat client admin detach-provider exit

An attach writes the [tun] or [peer] table it declares to the config file when the client booted from one, so it survives a restart. Detaching a provider takes down the pairs it serves. attach-peer without --exit brings the device up for routes you install yourself.

Linux only, on both ends. Each side opens a device, so each needs CAP_NET_ADMIN and /dev/net/tun; an exit provider also needs nft or iptables for the masquerade.

DHT discovery

For a server on a dynamic IP, --server dht publishes its address to the BitTorrent Mainline DHT and the client looks it up. The server signs the record with its private identity. The server public identity and that client's credential select and encrypt the record, so another client's credential cannot open it.

# Server publishes its address; IP is auto-detected from the DHT:
ZERONAT_SECRET="$SERVER_SECRET" ZERONAT_CLIENT_ID=client \
ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" zeronat server --server dht --tcp 443

# Client finds the server through the DHT:
ZERONAT_SECRET="$SERVER_PUBLIC" ZERONAT_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
zeronat client --server dht --tcp 443

--announce-ip <ip> overrides the detected IP and --announce-port <port> the announced port (default: the control port) when the server sits behind a port-forward. The client caches the last-known address and re-queries the DHT only when it stops working.

PPPoE proxy (znpppoe)

znpppoe opens many PPPoE sessions in userspace over one tunnel and exposes each as a SOCKS5 and HTTP CONNECT egress, each with its own ISP-assigned IP. It needs no kernel interface and no privileges. The server is a normal L2 bridge to the PPPoE segment (--tap, see above); the proxy credentials are separate from the PPPoE login, and the username selects the egress session.

docker run -d --name znpppoe -p 127.0.0.1:1080:1080 -p 127.0.0.1:8081:8081 \
  --user 65532:65532 --cap-drop ALL --security-opt no-new-privileges \
  -e ZN_SECRET="$SERVER_PUBLIC" -e ZN_CLIENT_SECRET="$CLIENT_CREDENTIAL" \
  -e ZN_USER=<pppoe-user> -e ZN_PASSWORD=<pppoe-pass> \
  -e ZN_PROXY_USER=proxy -e ZN_PROXY_PASS=<proxy-pass> \
  "ghcr.io/paltaio/znpppoe:${IMAGE_SHA}" --dht --connections 50 \
  --socks-listen 0.0.0.0:1080 --http-listen 0.0.0.0:8081

Set IMAGE_SHA to the published commit-SHA image tag. ZN_SECRET is the server public identity and ZN_CLIENT_SECRET is a server-issued client credential.

Both front ends share the password auth; the username picks the egress over the live sessions: proxy round-robins, proxy_pppoe<K> pins session K, and proxy_s<token> is sticky (one IP per token).

curl --socks5 proxy:<proxy-pass>@127.0.0.1:1080 https://ifconfig.me              # rotates
curl --proxy http://proxy_sjob42:<proxy-pass>@127.0.0.1:8081 https://ifconfig.me  # sticky

--peer <client-id> attaches the sessions to that client's L2 segment, served by another zeronat client running segment in its [peer] section; the frames ride a peer session between the two. It still names the server with --host or --dht, since the server is what pairs them. See Peer sessions.

Use --host <ip:port> instead of --dht for a fixed server. The ISP must allow concurrent PPPoE sessions on the login. Linux image, amd64 and arm64.

Scope

The public control port accepts UDP and TCP. Admission limits unauthenticated sockets, UDP source sessions, KCP conversations, and handshake work. Authenticated stateless datagrams reject duplicate and stale nonces while accepting bounded reordering.

Client credentials are bound to one configured client id. The server identity secret and admin secret grant different roles, and neither is a client credential. Protect /etc/zeronat/.env, client config files, and server config files with mode 600.
